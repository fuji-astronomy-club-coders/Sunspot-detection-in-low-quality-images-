# 太陽画像の座標正規化・4観測所比較機能 変更計画書

## 1. 目的と前提

本機能の目的は、固定された4か所の観測所から**同じ日付の太陽画像を1枚ずつ集め、合計4枚の解析結果を共通座標系で比較できるようにすること**である。

観測所ごとに太陽像の向き・大きさ・ピクセル分解能が異なるため、現在の画像左上原点の pixel 座標や矩形マスクをそのまま比較・共有することはできない。

本計画では、以下を前提とする。

- 比較対象のデータ提供元は4か所で固定する。
- そのうち3か所は組織的に運用され、画像の向きが継続的に変わらない想定とする。これらは観測所プロファイルに固定方向として登録する。
- 4か所目は方向が変わる可能性を考慮し、初期実装ではサンプルごとの方向入力を基本とする。後から固定であると確認できた場合は、観測所プロファイルへ移して日付ごとの入力を省略できる構造にする。
- 比較は同一日付の4観測所データを1組として行う。
- ピクセル分解能・観測日付・方向情報はユーザーが入力する。
- これらのサンプル情報を既存の \`src/config.yaml\` に列挙せず、専用の \`source_input/\` フォルダーで管理する。

**画像そのものは回転・反転・リサイズしない。** MIN2 が推定する太陽中心・太陽半径と観測所の北方向情報を使い、マスクと黒点座標だけを共通座標系へ変換する。

## 2. 対象範囲

### 実装する機能

- 4観測所のソース定義と、観測所ごとの向きの管理
- 同じ日付の4画像を1組として読み込む比較入力フォルダー
- 日付・ピクセル分解能・方向情報の入力と検証
- MIN2 が推定する太陽中心・太陽半径の共通利用
- 太陽中心を原点、北を +Y、太陽半径を 1 とする座標変換
- 共通座標系でのマスク保存・再利用
- 共通マスクを各画像のピクセル座標へ逆変換して黒点候補を除外
- 各画像の黒点 CSV と、4観測所をまとめた比較用 CSV の出力
- 変換条件・マスク条件・ソース情報のログ保存
- 従来の単一画像解析、pixel 座標、pixel 矩形マスクの互換性維持

### 今回は実装しない機能

- 画像データ自体の回転・反転・リサイズ・再サンプリング
- 画像を回転して表示するプレビュー UI
- 北方向の自動推定、FITS/WCS による姿勢推定
- 黒点特徴点を使った画像同士の自動位置合わせ
- 太陽表面の heliographic latitude / longitude への変換
- 観測時刻差による太陽自転・差動回転の補正
- 視線方向や太陽面傾斜を含めた三次元的な表面位置の復元
- 4観測所間で同一黒点を自動同定する処理。初期版では位置を比較できる共通座標と統合 CSV を提供し、同一黒点の対応付けは後続課題とする。

本機能が出力する座標は太陽円盤の**投影画像面上の相対座標**であり、太陽表面の緯度・経度そのものではない。

## 3. 入力データの構成

### 3.1 専用フォルダー

プロジェクトルートに \`source_input/\` を作成する。観測所の固定情報と、日付ごとのサンプル情報をここに分離する。

構成案：

\`\`\`text
source_input/
├─ sources.yaml                 # 固定4観測所のプロファイル
├─ mask_templates/              # 共通座標で保存したマスクテンプレート
│  └─ default.json
└─ 2026-11-02/                  # 同じ日付の比較データ一式
   ├─ comparison.yaml           # この日付の4サンプルのメタデータ
   ├─ source_01.tif
   ├─ source_02.tif
   ├─ source_03.tif
   └─ source_04.tif
\`\`\`

日付フォルダー名は例であり、実際は \`YYYY-MM-DD\` とする。画像ファイル名は任意とし、\`comparison.yaml\` から相対パスで参照する方式でもよい。入力画像を日付フォルダー直下に置くか、観測所ごとのサブフォルダーに分けるかは実装時に決める。初期版では上記のように直下に4枚を置く形を推奨する。

### 3.2 \`sources.yaml\`：4観測所の固定プロファイル

観測所は4つに固定し、それぞれに変更されない識別子を割り当てる。実際の観測所名は実装時に確定し、文書中の \`source_01\` ～ \`source_04\` は仮名とする。

プロファイルには次の情報を持たせる。

| 項目 | 内容 |
|---|---|
| source_id | 固定の観測所 ID |
| display_name | 表示名 |
| orientation_policy | \`fixed\` または \`per_sample\` |
| north_vector | \`fixed\` の場合の北方向ベクトル |
| flip_x | 共通 +X への左右反転指定 |

3つの安定した観測所は \`orientation_policy: fixed\` とし、ユーザーが登録した北方向ベクトルと反転状態を全日付で再利用する。残る1か所は、向きが固定であると確認できるまで \`per_sample\` とし、日付ごとの \`comparison.yaml\` で方向を入力する。

固定方向もユーザーが入力・登録するデータであり、プログラムが自動推定するものではない。プロファイルの変更履歴が追跡できるよう、実行ログには実際に使用した方向・反転値を必ず展開して記録する。

### 3.3 \`comparison.yaml\`：日付ごとのサンプル情報

1つの日付フォルダーに、必ず4観測所分のデータを登録する。

記載例：

\`\`\`yaml
comparison_date: "2026-11-02"
mask_template: "mask_templates/default.json"

samples:
  - source_id: source_01
    image: "source_01.tif"
    observation_date: "2026-11-02"
    pixel_scale_arcsec_per_pixel: 0.60

  - source_id: source_02
    image: "source_02.tif"
    observation_date: "2026-11-02"
    pixel_scale_arcsec_per_pixel: 0.75

  - source_id: source_03
    image: "source_03.tif"
    observation_date: "2026-11-02"
    pixel_scale_arcsec_per_pixel: 0.50

  - source_id: source_04
    image: "source_04.tif"
    observation_date: "2026-11-02"
    pixel_scale_arcsec_per_pixel: 0.80
    north_vector:
      x: 0.0
      y: -1.0
    flip_x: false
\`\`\`

数値は形式説明用の架空値である。

- \`comparison_date\`：比較対象の日付。
- \`source_id\`：4観測所のいずれか。重複・不足を許さない。
- \`image\`：日付フォルダーからの相対画像パス。
- \`observation_date\`：サンプル画像の観測日。4件すべてが \`comparison_date\` と一致すること。
- \`pixel_scale_arcsec_per_pixel\`：ユーザーが入力するピクセル分解能。初期版は等方ピクセルを前提とする。
- \`north_vector\` / \`flip_x\`：\`per_sample\` の観測所で必須。固定プロファイルの観測所では省略時に \`sources.yaml\` の値を使用できる。明示的な上書きを許可するかは初期運用で決めるが、固定方向の意図しない変更を防ぐため、初期版では固定値の上書きを原則禁止する案を推奨する。

日付・分解能は各サンプルについてユーザーが入力する。方向もユーザーが設定するが、3観測所は向きが変わらない前提で一度プロファイルへ登録し、日付ごとに繰り返し入力しない。4か所目はサンプルごとに入力する方式から開始する。処理開始時には、方向の実効値（プロファイル適用後の値）をログと比較結果へ保存する。

### 3.4 入力データの検証

比較処理を開始する前に、以下を検証する。

1. \`sources.yaml\` に定義された観測所がちょうど4か所で、ID が重複していない。
2. 日付フォルダーの \`comparison.yaml\` に4サンプルが登録されている。
3. 4サンプルの \`source_id\` がそれぞれ異なり、定義済み4観測所を1回ずつ含む。
4. 全サンプルの \`observation_date\` が \`comparison_date\` と一致する。
5. 参照画像が存在し、読み込み可能である。
6. ピクセル分解能が有限かつ正の値である。
7. \`per_sample\` の方向ベクトルが有限で、長さが0より大きい。
8. \`fixed\` の観測所に必要な北方向ベクトル・flip_x がプロファイルに設定されている。

検証に失敗した場合は、欠落・重複・日付不一致・画像不在などの原因をまとめて表示し、4枚のうち一部だけで比較処理を開始しない。4画像すべてが揃った場合のみ1組として処理する。

観測時刻が取得・入力可能な場合は任意項目として保存する。同じ暦日でも観測時刻が離れている可能性があるため、時刻が分かる場合は4件の時刻差を比較レポートに記録する。ただし初期版では時刻差による太陽自転補正は行わない。

## 4. 座標系と入力仕様

### 4.1 元画像の座標系

現状を維持する。

- 原点：画像左上
- +X：画像右方向
- +Y：画像下方向
- 単位：pixel

### 4.2 共通座標系

- 原点：MIN2 が推定した太陽中心
- +Y：登録・入力された太陽北方向
- +X：北方向に直交する方向。左右反転設定によって符号を確定する
- 単位：太陽半径を 1 とした無次元座標
- 太陽中心：(0, 0)、太陽の見かけの縁：おおむね原点からの距離 1

マスクや座標が太陽円盤外に存在する場合もあるため、座標を [-1, 1] に制限しない。

### 4.3 北方向ベクトル

北方向は固定観測所については \`sources.yaml\` に、\`per_sample\` の観測所については \`comparison.yaml\` にユーザーが入力する。

- ベクトルは画像ピクセル座標系で表現する。右が +X、下が +Y。
- 例えば (0, -1) は画像上方向、(1, 0) は画像右方向。
- ベクトルの長さは使用せず、方向だけを使う。
- (0, 0)、NaN、無限大は無効とし、理由を表示して比較処理を開始しない。
- ベクトル入力の代わりに画像上の北方向を示す点を入力する UI を設ける場合は、その点から MIN2 の太陽中心を引いてベクトルに変換する。これは入力 UI の選択肢であり、画像自体を回転する機能ではない。

各画像について実効的に使用した北方向ベクトルは、プロファイル値か日付別入力値かにかかわらず比較ログへ保存する。

### 4.4 左右反転と共通 +X

**北方向ベクトルだけでは、画像が鏡像になっているか判断できない。** \`flip_x\` は北方向とは独立して観測所プロファイルで管理する。\`per_sample\` の観測所では日付別に指定する。

共通 +X を太陽の東西どちらに対応させるかは実装前に決定し、4観測所すべてで同じ規約を使う。北方向ベクトルが一致しても、左右反転規約が誤っていれば黒点座標は左右反対になるため、4観測所の既知データで確認する。

## 5. 座標変換仕様

### 5.1 使用する値

| 記号 | 意味 |
|---|---|
| C = (cx, cy) | MIN2 が推定した太陽中心 |
| R | MIN2 が推定した太陽半径 [pixel] |
| N = (nx, ny) | プロファイルまたは日付別入力から解決した北方向ベクトル |
| P = (x, y) | 変換対象のピクセル座標 |

R は有限かつ正、北方向ベクトルは有限かつ長さが0より大きいことを検証する。

### 5.2 回転角

画像座標の Y 軸は下向きなので、次の角度を使う。

    theta = pi / 2 + atan2(ny, nx)

内部ではラジアンで保持する。北が画像上方向 (0, -1) の場合、theta は 0 となる。

### 5.3 元画像から共通座標へ

    dx = x - cx
    dy = y - cy

    X = (cos(theta) * dx + sin(theta) * dy) / R
    Y = (sin(theta) * dx - cos(theta) * dy) / R

    if flip_x:
        X = -X

画像の回転・反転・補間は行わず、点の座標だけを変換する。変換行列は次のとおり。

    A = [[ cos(theta),  sin(theta)],
         [ sin(theta), -cos(theta)]]

    q = A * (P - C) / R

flip_x が true の場合は、変換後の X 成分だけを反転する。

### 5.4 逆変換

共通座標で保存したマスク頂点を画像へ戻すときは、順変換と逆変換を独立した関数として実装する。回転・反転行列は直交行列であるため、逆行列は転置行列から求められる。順変換・逆変換の往復誤差を単体テストする。

## 6. 太陽半径とピクセル分解能

### 6.1 MIN2 の半径を主に使う理由

今回の主目的は、異なる画像に写る太陽円盤上の同じ相対位置を同じ座標で扱うことである。各画像で MIN2 が推定した太陽半径 R [pixel] を使い、太陽半径を 1 に正規化する。

例えば、画像ごとの太陽半径が 500 pixel と 800 pixel であっても、太陽中心からの相対位置を共通の無次元座標で表せる。

### 6.2 ピクセル分解能の使い道

ピクセル分解能 s [arcsec/pixel] はユーザーが日付別サンプル情報として入力する。相対座標の主スケールではなく、角度スケールの取得・整合性確認・将来の物理単位出力に使用する。

    solar_angular_radius_arcsec = solar_radius_px * pixel_scale_arcsec_per_pixel

ピクセル分解能が未入力の場合は、入力検証で比較処理を開始しない。MIN2 の半径だけでも数学的な相対座標変換は可能だが、今回の4観測所比較ではサンプル情報を揃える運用とする。

初期版は等方ピクセルを前提とする。将来 X・Y 別の分解能を入力できるようにデータ構造は拡張可能にするが、X・Y 分解能が異なる場合の異方性補正は初期実装に含めない。異なる値が入力された場合は警告または処理不可とし、楕円補正を別途設計する。

### 6.3 MIN2 の結果を共有する

現在は \`limb_darking_resolution.polynomialFit()\` 内で MIN2 を呼び出し、中心・半径を取得しているが、後段処理から同じ値を再利用できる構造になっていない。

変更後は、MIN2 の結果を SolarGeometry 相当のデータ構造（中心 X・Y、半径、必要な推定情報）として取得し、周縁減光補正と座標変換の双方へ渡す。同じ画像に対して MIN2 を重複実行しない。

既存の \`polynomialFit()\` の呼び出し互換性を維持するため、geometry 引数は任意引数とする。geometry が渡されない既存の利用方法では、従来どおり関数内で取得できるようにする。

## 7. 共通マスク

### 7.1 保存形式

マスクを元画像の矩形 (x, y, width, height) のまま共有しない。基準画像で選択した矩形の四隅を共通座標へ変換し、共通座標系上の多角形として保存する。

元画像上の矩形は、回転補正後の共通座標では一般に四角形となる。将来の拡張性を考え、頂点数を固定しない多角形形式にする。

保存ファイル案：\`source_input/mask_templates/default.json\`

    {
      "schema_version": 1,
      "coordinate_system": "solar_disk_normalized",
      "regions": [
        {
          "id": 1,
          "vertices": [[-0.25, 0.10], [0.15, 0.10], [0.15, 0.35], [-0.25, 0.35]]
        }
      ]
    }

上記の座標値は形式説明用である。テンプレートには元画像の pixel 座標を正本として保存しない。作成元の観測所 ID、画像名、日付、太陽 geometry、北方向ベクトル、flip_x などは履歴情報として保存する。

### 7.2 作成・再利用

初期版では既存のマスク選択 UI を利用する。比較対象のうち1枚を基準画像として矩形を選択し、その四隅を共通座標へ変換してテンプレートに保存する。同じテンプレートをその日付の残り3画像へ適用する。テンプレートは日付フォルダーとは別の \`source_input/mask_templates/\` に保存し、必要に応じて別日付の比較でも再利用できるようにする。

今回、マスク UI 自体を画像回転表示に対応させることは必須要件にしない。

### 7.3 適用

各画像で、共通座標の多角形頂点を逆変換してピクセル座標へ戻し、ラベル画像上に多角形マスクを適用する。

- 元画像の画素値は変更しない。
- 既存の「マスクに1画素でも重なる黒点候補ラベルを候補単位で除外する」動作を維持する。
- 頂点は浮動小数点で保持し、ラスタライズ時にのみ画素格子へ変換する。
- 画像外の領域はラスタライズ時にクリップする。正規化座標自体は切り詰めない。
- マスクごとの重複候補数、除外ラベル、適用範囲を従来どおりログに記録する。

共通マスク機能が無効の単一画像解析では、既存の pixel 矩形マスクをそのまま利用し、従来結果を変えない。

## 8. 比較処理と出力

### 8.1 4画像の処理フロー

新しい比較処理は、日付フォルダーを1単位として実行する。

1. \`sources.yaml\` と \`comparison.yaml\` を読み込む。
2. 4観測所分の画像・日付・ピクセル分解能・方向情報を検証する。
3. 各画像について MIN2 の太陽中心・半径を取得する。
4. 観測所プロファイルとサンプル情報から方向・flip_x を解決する。
5. 4画像をそれぞれ既存の周縁減光補正・強調・黒点検出処理に渡す。
6. 共通マスクを各画像の pixel 座標へ逆変換し、候補を除外する。
7. 各画像の個別 CSV と、4画像を統合した比較用 CSV を出力する。

既存の単一画像実行フローは残す。比較モードは既存処理を4回呼び出す上位のオーケストレーションとして追加し、検出アルゴリズムを二重実装しない。

### 8.2 出力フォルダー案

    results/
    └─ comparison_2026-11-02/
       ├─ comparison_summary.json
       ├─ comparison_sunspot_statistics.csv
       ├─ source_01/
       │  ├─ sunspot_statistics.csv
       │  ├─ sunspot_exclusion_list.csv
       │  └─ 実行ログ・既存の解析成果物
       ├─ source_02/
       ├─ source_03/
       └─ source_04/

個別結果は既存の CSV 仕様を基本的に維持する。統合 CSV には \`comparison_date\`、\`source_id\`、\`image\`、\`centroid_x_normalized\`、\`centroid_y_normalized\` を含め、個別 CSV の pixel 座標や面積なども必要に応じて保持する。

統合 CSV は4観測所の検出点を共通座標で並べるものであり、異なる観測所の同一黒点を自動で同定した ID を付与するものではない。同一黒点の対応付け・検出漏れ比較は後続機能とする。

## 9. 黒点 CSV の変更

既存の pixel 座標列は削除・改名しない。元画像での再確認や既存スクリプトとの互換性のために残し、共通座標の重心列を追加する。

\`sunspot_statistics.csv\` と \`sunspot_exclusion_list.csv\` に次の列を追加する。

| 列名 | 内容 |
|---|---|
| centroid_x_normalized | 共通座標系に変換した重心 X |
| centroid_y_normalized | 共通座標系に変換した重心 Y |

\`centroid_x_px\` / \`centroid_y_px\` は従来どおり画像左上原点の pixel 座標とする。

既存の bbox 列も元画像上の外接矩形として残す。回転後の形状は矩形とは限らないため、これらを共通座標の外接矩形と誤認させない。共通座標での形状比較は初期版では必須とせず、必要になった段階で輪郭頂点や共通座標の外接範囲を追加する。

任意の追加指標として \`area_px / (pi * R**2)\` による円盤面積比を検討できるが、初期必須項目は重心の共通座標化とする。面積の物理換算はピクセル分解能の信頼性を確認してから追加する。

## 10. 設定とログ

### 10.1 \`config.yaml\` の扱い

サンプルごとの日付・画像パス・ピクセル分解能・方向ベクトルを \`src/config.yaml\` に列挙しない。これらは \`source_input/\` 以下で管理する。

既存の \`config.yaml\` には、通常の画像処理パラメータを残す。比較処理の起動に必要な場合でも、追加するのは \`source_input/\` のルートパスなど最小限の指定だけとする。既定の \`source_input/\` を使う場合は追加設定そのものを不要にする。

### 10.2 ログに残す情報

- 比較 ID・比較日付・固定4観測所の ID
- 各画像のパス・観測日付・観測時刻（入力された場合）
- 各画像のピクセル分解能
- MIN2 の太陽中心 (cx, cy) と半径 R
- 実際に使用した北方向ベクトルと、固定プロファイル／日付別入力のどちらから取得したか
- 回転角 theta、flip_x、変換行列、座標系のバージョン
- マスクテンプレートのパス・schema version
- 共通マスク／従来 pixel マスクのどちらを使用したか
- 変換後のマスク頂点、重複候補数、除外候補ラベル
- 4観測所すべての入力検証結果と処理結果

## 12. 実装段階と完了条件

### Phase 1：固定4観測所と入力フォルダー

1. \`source_input/\` の標準構成を作る。
2. \`sources.yaml\` に固定4観測所を登録する。
3. 向きが安定している3か所を \`fixed\`、残りを初期状態で \`per_sample\` として管理する。
4. 日付ごとの \`comparison.yaml\` を読み、4画像・同一日付・分解能・方向を検証する。
5. 不足・重複・日付不一致がある場合は比較処理を開始しない。

完了条件：サンプル情報が \`config.yaml\` に混在せず、同じ日付の4観測所データだけが比較処理に渡される。

### Phase 2：太陽 geometry と方向の共通化

1. MIN2 の結果を SolarGeometry として取得する。
2. 既存の周縁減光補正と座標変換に同じ geometry を渡す。
3. 固定プロファイルと日付別入力から方向情報を解決する。
4. 順変換・逆変換、flip_x を独立モジュールに実装する。
5. 変換パラメータをログに保存する。

完了条件：MIN2 を同じ画像に対して重複実行せず、既知の方向で北が共通 +Y となり、往復変換誤差が許容範囲内に収まる。

### Phase 3：共通マスクテンプレート

1. 基準画像で選択した矩形 ROI の四隅を共通座標へ変換する。
2. 多角形 JSON として \`source_input/mask_templates/\` に保存・読み込みする。
3. 4画像それぞれで逆変換し、多角形マスクをラベル画像へ適用する。
4. 既存 pixel 矩形マスクを維持する。

完了条件：回転角度・太陽半径の異なる4画像でも、同じ共通領域が対応する。

### Phase 4：4画像比較と CSV・ログ

1. 既存の単一画像解析を4サンプルに対して実行する比較統括処理を追加する。
2. 各画像の個別 CSV に共通座標の重心列を追加する。
3. 4観測所の結果をまとめた \`comparison_sunspot_statistics.csv\` を追加する。
4. CSV ガイドと実行ログを更新する。

完了条件：同一日付4観測所の検出結果を1つの比較用 CSV で確認でき、各行の観測所・画像・変換条件を追跡できる。

### Phase 5：総合検証

1. 回転角・太陽半径・画像中心が異なる人工画像で共通座標を比較する。
2. 固定3観測所の方向プロファイルが日付をまたいで再利用されることを確認する。
3. per_sample の方向が日付ごとに正しく適用されることを確認する。
4. 左右反転あり・なしを検証する。
5. 実観測画像4枚で MIN2 と北方向入力の妥当性を確認する。
6. 既定設定の単一画像解析で従来動作が維持されることを確認する。
7. Ruff、Basedpyright、既存 CI を通過させる。

## 13. テスト計画

### 入力データ

- 4観測所がすべて存在し、各 ID が1回ずつ登録されている場合に読み込める。
- 3件以下、5件以上、ID 重複、未定義 ID の場合は比較開始前にエラーになる。
- 1件でも日付が異なれば比較全体を開始しない。
- 画像ファイル欠落・読み込み失敗を検出する。
- 分解能が0、負値、NaN、無限大の場合を拒否する。
- per_sample の方向ベクトルがゼロ・非有限値の場合を拒否する。
- fixed の観測所が日付マニフェストで方向を省略した場合、プロファイル値が使われる。
- プロファイルに必要な固定方向がない場合はエラーになる。

### 座標変換

- 北が画像上 (0, -1) のとき、変換後の北が (0, +1) になる。
- 北が右 (1, 0)、下 (0, 1)、左 (-1, 0)、任意の斜め方向の場合も成立する。
- ベクトルの長さだけを変えても変換結果が変わらない。
- flip_x は X の符号だけを変え、Y を変えない。
- 太陽中心が常に (0, 0) になる。
- 太陽半径上の点は原点からの距離がおおむね 1 になる。
- 順変換と逆変換で元の pixel 座標に戻る。
- ゼロベクトル、非有限値、半径 0 以下を拒否する。

### 観測所間比較

同じ正規化座標にある人工黒点を、中心・半径・回転角の異なる4画像へ配置する。各画像の入力メタデータを使い、変換後の座標が一致することを確認する。3つの固定方向は異なる日付の比較でも同じ値が使われ、per_sample の方向は日付ごとに変更できることを確認する。左右反転画像では正しい flip_x を与えた場合に一致することを確認する。

### マスク

- 基準画像で作成したマスクが、同じ日付の他3画像でも同じ共通領域に対応する。
- 回転後の矩形が多角形として正しく表現される。
- マスク境界付近の画素処理が一貫する。
- 複数マスクに重なる候補は1回だけ除外し、該当する全マスク ID を記録する。
- 画像端・画像外へはみ出すマスクを安全に処理する。
- 従来の pixel 矩形マスクのテスト結果が変わらない。

### 回帰・統合出力

- 比較モードを使わない場合、従来の単一画像処理結果が変わらない。
- geometry の共有後も周縁減光補正画像が変わらない。
- 個別 CSV の既存列・除外一覧・ログに後方互換性がある。
- 統合 CSV に必ず4つの source_id が出力される。
- 比較入力が不正な場合、一部の画像だけを処理した不完全な比較結果を作らない。
- Ruff、Basedpyright、既存 CI を通過する。

## 14. 利用者から見た機能変化

### 変更前

- 画像を1枚ずつ指定して解析する。
- サンプルごとの情報が比較処理向けにまとまっていない。
- マスクは画像左上原点の pixel 座標で指定する。
- 観測所ごとに太陽の向き・大きさが異なり、同じマスク座標をそのまま再利用できない。
- 黒点 CSV の座標は画像ごとの pixel 座標なので、観測所間で直接比較しにくい。

### 変更後

1. \`source_input/\` に4観測所の画像とメタデータを置く。
2. 3観測所の安定した方向は一度プロファイルに登録し、残る観測所の方向は日付ごとに入力する。
3. 比較したい日付のフォルダーを選択して実行する。
4. プログラムが4観測所分のデータ・日付・分解能・方向を検証する。
5. MIN2 の太陽中心・半径を基準に、中心が原点、北が +Y、太陽半径が 1 の共通座標へ変換する。
6. マスクを共通座標の多角形として保存し、同じ日付の4画像へ適用する。
7. 各画像の個別結果と、4観測所の黒点座標をまとめた比較用 CSV を出力する。

\`config.yaml\` は従来どおり画像処理アルゴリズムの設定を中心に保ち、サンプル情報は \`source_input/\` へ分離する。元画像の画素値・向き・大きさは変化せず、画像回転による補間の影響を受けない。

### 利用上の注意

- 4観測所すべてのデータが同じ日付で揃わない場合、その比較セットは実行できない。
- 同じ日付でも観測時刻は異なり得る。時刻差は記録するが、初期版では太陽自転補正を行わない。
- 北方向ベクトルの入力誤差はマスク位置と黒点座標の両方に影響する。
- 北方向だけでは左右反転を判断できないため、観測所プロファイルの flip_x を正しく設定する必要がある。
- MIN2 の中心・半径が不正確な画像では、正規化座標も不正確になる。
- ピクセル分解能はユーザー入力値であり、入力誤りが角度スケールの確認・将来の物理単位換算に影響する。
- 太陽半径による正規化は円盤上の相対位置比較に適するが、太陽表面の緯度・経度を直接表さない。
- 比較用 CSV は4観測所の検出点を共通座標で並べるもので、同一黒点の自動対応付けは行わない。

## 15. 実装着手前に確定する事項

1. 4観測所の正式な ID と表示名。
2. 安定した3観測所の北方向ベクトルと flip_x の初期値。
3. 4か所目をサンプルごとの方向入力で運用開始するか、最初から固定方向として登録できるか。
4. 共通 +X を天文学上の東・西のどちらにするか。
5. ピクセル分解能の入力単位・精度、および X・Y 別の値が提供される可能性。
6. マスクテンプレートを全日付で共通利用するか、日付・観測目的ごとに切り替えるか。
7. 観測時刻を入力可能か。入力できる場合、どの形式・タイムゾーンで保持するか。
8. 4観測所の比較用 CSV に、共通座標の重心以外にどの指標を含めるか。

正式な観測所名と方向値が確定するまでは、\`source_01\` ～ \`source_04\` の仮 ID で実装できる。3観測所の向きが安定している前提は、ユーザーが登録したプロファイル値を再利用することで反映する。
